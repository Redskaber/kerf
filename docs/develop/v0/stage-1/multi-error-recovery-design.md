# TD-013 多错误收集与 Expander 恢复展开设计（批次 C 设计批）

> **Author**: kerf-dev-agent（ARCH-A 角色）
> **Date**: 2026-09-10（r7，Stage 1 批次 C）
> **Version**: v0.1.0-r7
> **Status**: Accepted（设计冻结——实现绑定批次 E）

## 1. 问题与范围

**现状（TD-013，P2）**：管线为单错误短路——首个错误终止编译，后续形式不再
展开/求值。`negative_semantics_tests::error_recovery_*` 4 case 锚定当前
事实行为。设计承诺（02-语法模型 §5 / 08-7）为「单次运行报告多个错误 +
Expander 错误恢复后继续展开后续形式（IDE 增量反馈）」。

**本设计批范围**：恢复模型与收集策略的架构裁定。**不含**实现——实现
绑定批次 E（Expander kerf 重写时随新展开器一并落地，避免在 Rust 展开
器上做两套恢复机制后又在重写期返工，§12 最优>最小）。

## 2. 恢复模型（形式级恢复，表达式级不恢复）

```
源文件 = 形式₁ 形式₂ 形式₃ …
              ↓ expand_program
形式ᵢ 报错 → 诊断入收集器 → 跳过形式ᵢ → 继续形式ᵢ₊₁
              ↓
收集器（Vec<Diagnostic>，按 Span 次序排序）→ 统一渲染
```

- **恢复粒度 = 顶层形式（form-level）**：一个形式出错，后续顶层形式
  继续展开。形式内部（嵌套表达式）不恢复——嵌套错误的单条上报已足够
  定位修复（IDE 场景用户按首错修复后重跑）。
- **理由**：表达式级恢复需要错误后状态重建（半展开的 Stx 树处于不一致
  状态——相位簿记/变换器注册已部分完成），复杂度与收益不成比例；
  形式级跳过天然保持形式间独立性（kerf 顶层形式无隐式数据流）。
- **上限防护**：`MAX_DIAGNOSTICS = 128`（诊断风暴防护——错误连坐的
  宏模板会在一个形式内产生级联错误）。达到上限后停止收集、报告
  「诊断数截断」提示（warning 级）。

## 3. 收集器契约（Diagnostic 是数据——§8.7 架构原则）

```rust
/// 多错误收集器（批次 E 落地于 kerf-expander）。
pub struct DiagCollector {
    diags: Vec<Diagnostic>,   // 收集即追加（Span 次序在导出时排序）
    truncated: bool,          // 达到上限后截断标记
}
impl DiagCollector {
    pub fn push(&mut self, d: Diagnostic);          // 追加（超过上限 → truncated）
    pub fn is_full(&self) -> bool;                  // 恢复循环的提前终止信号
    pub fn into_sorted(self) -> Vec<Diagnostic>;    // 按 (file_id, start, end) 排序导出
}
```

- 排序口径与 `check_program`（批次 C 已交付）一致：`(file_id, start, end)`
  稳定排序——**多错误的输出次序与源码位置对齐**（用户按从上到下阅读
  顺序修复）。
- 渲染复用 `render_diagnostic`（§2.2 原则 16：人类可感知输出）——逐条
  渲染 + 末尾汇总行「发现 N 个问题」。

## 4. 与 Effect 处理的联动裁定（08-7 §6.4 同批设计约束）

多错误收集的恢复策略与 effect handler continuation 语义**同批设计**
（TD-013 登记时的绑定条件），裁定如下：

- **编译期恢复 ≠ 运行期 continuation**：Expander 的形式级恢复是
  **编译期**控制流（跳过源码形式），不是 effect handler 的运行期
  continuation 捕获/恢复。二者共用「错误是数据」的表示（Diagnostic
  值），但恢复机制分离——不把编译期恢复实现为 effect（那会把展开器
  的内部控制流暴露到语言语义面，违反 §11 接口隔离）。
- **Stage 2 复核点**：effect handler 语言级暴露（07 §3.4）时复核本
  裁定——若届时需要「错误恢复作为可编程策略」（用户自定义恢复），
  以 effect 重述编译期恢复属 Stage 2+ 演进，本设计不预留钩子（预留
  会引入 P3 级投机接口，违背 §21.7 引入时机判据）。

## 5. 消费面（已实证部分 + 批次 E 扩展）

| 消费方 | 状态 | 多错误行为 |
|--------|------|-----------|
| `kerf check`（批次 C，r7 已交付） | ✅ 实证 | 静态检查全量收集（R1-R8 规则独立触发，互不短路）——**本设计的首个活体消费面**：`check_source` 返回 `Vec<Diagnostic>`，`typecheck_tests::multi_error_collection_span_order` 断言三错误全量 + Span 次序 |
| Read/Expand/Compile 管线错误 | 批次 E | 形式级恢复 + 收集器接入 `expand_program`（返回 `Result<Vec<CoreExpr>, DiagCollector>` 形态——错误与产物共存：部分成功的形式照常编译，仅当收集器非空时整体退出码非零） |
| run/eval 执行路径 | 不变 | 执行期错误维持单错误短路（运行期状态不可回滚——形式级恢复只属编译期） |
| IDE/LSP（Stage 2+） | 规划 | 诊断流式消费（收集器 → LSP publishDiagnostics） |

## 6. 验收标准（批次 E 实现时）

1. 形式级恢复：`(define x 1) (car) (define y 2)` → 报「car 元数」错误
   **且** `y` 的定义正常展开（编译产物含 y）；
2. 收集上限：构造 > 128 错误的程序 → 输出 128 条 + 截断提示；
3. 次序：多错误的渲染顺序 = 源码位置顺序（与 check 一致）；
4. 既有 408 测试全绿（单错误路径的断言不受影响——恢复只在「首个错误
   后还有形式」的场景改变行为）；
5. 负向测试 ≥12 case（恢复正确性 / 跳过形式不影响后续 / 上限 / 次序 /
   部分产物语义）。

## 7. 决策记录

| 决策 | 裁定 | 依据 |
|------|------|------|
| 恢复粒度 | 形式级（非表达式级） | 半展开状态重建成本 vs IDE 反馈收益；§12 最优>最小 |
| 恢复机制 | 编译期控制流（非 effect） | §11 接口隔离——展开器内部不进语言语义面 |
| 收集上限 | 128 + 截断提示 | 诊断风暴防护（宏模板级联错误） |
| 实现时机 | 批次 E（Expander kerf 重写同批） | 避免双恢复机制返工；登记册绑定条件 |
| 执行路径 | 不恢复（维持短路） | 运行期状态不可回滚；恢复属编译期职责 |

*遵循条款：§8.7（错误是数据）、§12（最优>最小——单批单恢复机制）、
§11（接口隔离——编译期/运行期恢复分离）、§21.7（引入时机——不为
Stage 2+ 预留投机钩子）、TD-013 登记项（效应时机同批设计绑定）。*
