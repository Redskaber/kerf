## 3. 历史教训归档

### Stage 0: 同构构造点的批量缺陷
- **现象**：lambda 体铺平 bug 在 4 处同构构造点重复出现
- **根因**：手工构造 Stx 时「列表包装 vs 铺平」语义不显式
- **对策**：同类路径审查（§20.3）已执行；后续引入构造辅助函数
  （`make_lambda_form(params, body_forms)`）收口

### Stage 1 批次 B 收官（r6，B3 自举 Reader）
- **现象**：手写 kerf 源码（reader.krf）的首两处缺陷均为「表示层语义
  错位」——① `'nil`/`'true`/`'false` 引用后是字面量 datum（TD-002 语义）
  而非符号，节点 tag 需 `string->symbol` 构造；② 结果解构字段序错位
  （`second` 取到 kind 而非 payload）。两处均被既有测试立即暴露。
- **根因**：跨表示边界（Rust 值 ↔ kerf 值）的字段/tag 约定无类型检查
  兜底——kerf 侧是动态值编程。
- **对策**：契约文档化（reader.krf 文件头编码规范）+ parity 套件的
  逐字节断言（表示层错位 → 立即消息/Span 不一致失败）；后续桥侧可
  评估 debug_assert 字段形态校验。
- **校准结论（滚动）**：双实现 parity 是「重写类 MUV」的最优验收形态
  ——比单向快照多锁一个维度的行为契约（错误次序/字节口径），且增量
  成本仅是对照走查函数（~60 行）；系统化负例矩阵（266 case 语料）
  以极低成本（数据行）维持 §9.4.3 正负比。

### Stage 1 批次 C（r7，类型检查器 + 编译缓存）
- **现象**：typecheck 深度预算初值 2000 在 debug 构建下单测栈溢出
  （2 MiB 线程栈）；同批发现 Reader 嵌套上限 256 使源文本永不可达
  2000 深度——预算阈值的两条约束（栈安全 × 可达性）在集成前未同框
  评估。
- **根因**：debug 构建帧尺寸（~1 KiB/帧）与 release 差异未被预算
  定标吸收；「Reader 256 上限」这一上游约束未进入检查器的预算
  依据链。
- **对策**：预算 = 上游上限（256）× 2 = 512（4× 栈安全余量），依据
  链写入常量文档；超预算路径经**程序化构造**的单测覆盖（源文本不可
  达的面用构造面测试——「不可达 ≠ 不必测」）。
- **校准结论（滚动）**：① 递归预算类常量必须携带「debug 帧 × 栈」
  实测定标与上游上限依据（双向：过深溢出 / 过浅漏检）；② 集成测试
  不可达的路径（如超深表达式）以程序化构造在单元层补测；③ 缓存类
  功能的验收锚 = 「命中产物 == 新编译产物」（确定性证明）而非仅
  行为等价——BcProgram PartialEq 是免费的逐字节证明器。
